# Единая валюта отображения бюджета

Статус: реализовано и проверено локально, 17.10.2026. Подтверждение CI и production rollout фиксируется отдельно при выпуске.

## Требования

- Единый переключатель валюты в шапке для главной, операций, отчётов, накоплений и инвестиций. Сохранять выбор для активного бюджета в браузере; переключение не меняет базовую валюту бюджета или валюту ввода операций.
- Операции сохраняют исходную сумму/валюту; в списках показывать исходную сумму и эквивалент в валюте интерфейса. Все агрегаты одного экрана имеют одну выбранную валюту.
- Доходы и расходы пересчитывать для каждой операции по последнему известному курсу не позднее даты операции, затем суммировать. Не использовать сегодняшний или будущий курс для исторических расходов. В выходные отдельная котировка не требуется.
- Накопления и текущую стоимость инвестиций оценивать на дату оценки по существующим правилам; исторические инвестиционные расчёты сохраняют свои даты оценки.
- Ручной ввод курса не требуется. Исторические операции и движения при смене валюты интерфейса не переписывать.
- Telegram: без указания валюты RUB (существующую явно выбранную настройку пользователя сохранить); распознавать коды без учёта регистра, символы, русские названия и словоформы. Примеры: `20 евро продукты`, `20€ продукты`, `$20 такси`, `20 usd такси`, `20 долларов такси`. Явная валюта сообщения приоритетнее настройки.

## Проверенные границы

- `internal/domain/transaction.go`, `migrations/0003_transactions.up.sql`: исходная сумма, base_amount и FX snapshot уже существуют. `internal/adapter/postgres/transaction_repo.go` вычисляет base_amount через NUMERIC при записи.
- `internal/usecase/report/service.go`: оба отчёта принимают target currency, но конвертируют сохранённый base_amount через базовую валюту. Это создаёт лишнее округление и не гарантирует точное совпадение с исходной суммой при выборе её валюты.
- `proto/budget/v1/transaction.proto`: GetTransactionsTotals не принимает целевую валюту. PostgreSQL суммирует base_amount.
- `web/app/page.tsx`, `web/app/reports/page.tsx`: targetCurrencyCode пустой; переключателя нет. В NewTransactionForm уже есть RUB/EUR/USD и другие поддерживаемые валюты.
- `internal/adapter/postgres/fx_repo.go`: GetRateAsOf использует BatchGetRates, ограничение as_of <= дата операции, обратные и кросс-пары через RUB уже доступны. История автоматического импортера начинается с 01.01.2025 (исходный срез может быть раньше).
- Бот — соседний репозиторий `../budget-bot`. `internal/bot/currency_parser.go` распознаёт символы и отдельные ISO-коды, но не русские названия; `parser.go` и `handler.go` передают явную валюту и применяют preferences для отсутствующей.

## План реализации

1. Ввести общий web provider/hook валюты отображения, подключить к layout и HeaderNav. Изолировать сохранение по бюджету, согласовать переключение вкладок и ключи React Query. Перевести существующие локальные переключатели накоплений/инвестиций на общее состояние; при отсутствии нового выбора использовать существующую настройку активного бюджета, затем RUB.
2. Общий серверный расчёт эквивалента из исходной суммы в целевую валюту на дату операции, с точной арифметикой и единым округлением. В исходной валюте возвращать исходную сумму. Не делать последовательную конвертацию через округлённый base_amount. Существующие snapshot-поля не переписывать; отдельно проверить согласованность исторических ручных курсов и сохранённых snapshot при реализации.
3. Подключить расчёт к обоим отчётам и GetTransactionsTotals. Добавить обратно совместимое target_currency_code в запрос итогов, при необходимости поля эквивалента в чтение операций; регенерировать Go/TS и клиенты бота. Фильтры исходной валюты/суммы сохранить с явными подписями. Курсы читать пакетно по уникальным датам/валютам, избегать запроса на каждую операцию.
4. Подключить выбранную валюту к главной, списку и итогам операций, обоим отчётам/графикам, накоплениям и инвестициям. Убрать дублирующие локальные переключатели, показывать исходные суммы рядом с эквивалентами. Валюта отображения не должна менять валюту создания операции.
5. В budget-bot расширить детерминированный парсер: словоформы EUR/USD/RUB, символ до/после суммы, слитные коды вроде `20eur`, дроби с точкой/запятой. Не извлекать валюту из частей обычных слов; несколько конфликтующих валют отклонять с понятным ответом. Проверить сохранение валюты через ручной выбор категории, LLM-путь, состояния и gRPC, подтверждение и recent/stats.
6. Проверить историческое покрытие до первой валютной операции. Если ни одной котировки не существует не позднее даты операции, автоматически загрузить необходимую историю существующим FX-механизмом; при недоступном источнике не подставлять будущий курс, единицу или ноль. Это исключительный технический сбой, его показывать явно. Обычный fallback на предыдущую дату уже реализован.

## Проверки и выпуск

- Go: общий расчёт, отчёты и итоги на смеси RUB/EUR/USD; исходная валюта возвращается без потерь; кросс-пары, выходные, предыдущая котировка, отсутствие будущих курсов, округление и большие суммы. Проверить границы календарной даты операции при смене часового пояса.
- PostgreSQL integration: реальные NUMERIC snapshot при записи/редактировании, итоги и отчёты по одинаковым фильтрам, историческая выборка котировок; для изменённого SQL проверить планы на представительном объёме.
- Web: переключение в шапке обновляет все суммы/графики, сохраняется после перезагрузки, разделено по бюджетам, не меняет ввод и журнал. Проверить RU/EN и мобильную шапку.
- Bot: таблица вариантов валют/дробей/дат, без валюты RUB, сохранённая настройка, явный EUR поверх RUB, конфликтующие валюты; пройти цепочку до CreateTransactionRequest.
- Миграция денежных данных заранее не требуется: необходимые исходные поля есть. Нужны обратно совместимые protobuf-добавления и проверка истории курсов. Новую схему БД вводить только при доказанной необходимости.
- Сначала backend с совместимым API, затем web и bot. Локальные тесты, CI, rollout и проверку опубликованного интерфейса фиксировать отдельно. Коммиты, push и deployment в эту подготовку плана не входят.

## Реализованное поведение

- `web/lib/display-currency.ts` и `DisplayCurrencySelect`: один выбор RUB/USD/EUR в шапке, синхронизация независимых потребителей и вкладок, сохранение по бюджету. Старый выбор накоплений переносится при первом чтении, если это одна из трёх общих валют. Валюта ввода остаётся независимой. Локальные переключатели накоплений, портфеля и календаря удалены.
- Главная, список/итоги операций, оба бюджетных отчёта, портфель/рост/карточка инструмента и календарь читают общее состояние. У затронутых страниц убраны вложенные ClientsProvider: используется провайдер layout. Ключи бюджетных сумм включают tenant и валюту.
- `transactionfx.Converter`: исходная сумма без обратного округления в её валюте; при выборе записанной базовой валюты сохраняется существующий FX snapshot. Остальные валюты пересчитываются напрямую из исходной суммы по историческому курсу. Расчёты точные, с проверкой переполнения. Курсы пакетно выбираются по валютам на уникальные даты и кешируются в рамках запроса.
- Обратно совместимые поля: `Transaction.display_amount`, `ListTransactionsRequest.target_currency_code`, `GetTransactionsTotalsRequest.target_currency_code`. Пустая целевая валюта сохраняет прежнее поведение клиентов.
- Сравнение полученных инвестиционных выплат также принимает `GetInvestmentPayoutsRequest.target_currency_code`: агрегаты и годовая база пересчитываются по датам отдельных выплат, исходные записи страницы сохраняются. Используется точная рациональная инвестиционная арифметика и общий исторический FX; чтение курсов и операций происходит в одном repeatable-read snapshot. Старый запрос без валюты сохраняет группировку по исходным валютам.
- Фоновый FX importer проверяет наиболее раннюю операцию бюджета/инвестиций. При необходимости расширяет историю EUR/USD до этой даты; для дат до 2025 года не требует котировок позднее появившихся валют (например GEL). С 2025 года импортируются прежние девять валют. На старте импорт идемпотентен, новые более ранние операции обнаруживаются при очередной часовой проверке. Если данные ещё загружаются или источник недоступен, UI показывает ошибку пересчёта, не фиктивный ноль/курс 1. Для создания операции до всей доступной истории сначала требуется загрузить историю соответствующего периода через fximport; будущие котировки не используются.
- Telegram реализован в соседнем budget-bot, правила и проверки: `../../budget-bot/docs/multicurrency.md`.

## Локальная проверка

- 288 web unit-тестов, 38 Playwright сценариев и сборка web; тесты серверных transactionfx/transaction/report/fximport/cbr/investment/grpc; go vet затронутых usecase и адаптера ЦБ; сборки budgetd и budget-bot; buf lint.
- Настоящий одноразовый PostgreSQL 16: TestBudgetMulticurrency_PG, TestFxImportAndCrossRates_PG, TestInvestmentPayoutsPersistedFactsAndIsolation. Проверены FX snapshot, воскресная дата до понедельничного курса, совпадение списка/итогов/отчётов, точная конвертация инвестиционных выплат и сохранение исходных валют.
- Playwright использует локальную production-сборку с `NEXT_PUBLIC_GRPC_BASE_URL=http://127.0.0.1:3030/grpc`, синтетический gRPC и исходящие финансовые записи не выполняет. Новые RU/EN сценарии проверяют переключение/сохранение/переходы через бюджет, накопления, инвестиции и календарь, запросы валюты и шапку на ширине 390px.
- Production-данные и фактическое покрытие курсов на сервере не проверялись. Порядок выпуска: совместимый backend, затем web и bot; после завершения импорта истории проверить реальные отчёты отдельно.

Предрелизная сверка: сводный отчёт разбирает даты в переданном часовом поясе клиента (включая Испанию), обе формы отчёта имеют одинаковые границы периода. Порядок страниц операций дополнен уникальным id, чтобы одинаковое время операций не приводило к пропускам/повторам при суммировании более 500 строк.
