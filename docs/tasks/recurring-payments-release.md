# Регулярные платежи: реализация и выпуск

Дата: 18.10.2026. Первый веб-этап реализован локально; публикация и production rollout не выполнялись.

## Что добавлено

- `/payments`: месячные начисления, фильтры, поиск, общие суммы независимо от страницы; шаблоны и архив.
- Фиксированные и переменные платежи, календарные месяцы/кварталы/годы, IANA timezone, последний день месяца, период услуги.
- Изменение шаблона с предпросмотром новых дат со следующего месяца; сохранение истории и ручных исключений. Архив сохраняет долги.
- Атомарная оплата новым расходом или привязка существующего. Общая транзакция БД включает расход, движение счёта, связь и результат идемпотентности. Блокировка tenant сериализует генерацию и финансовые команды; версии защищают изменения начислений.
- Снятие связи сохраняет расход. Удаление расхода каскадно снимает связь. Несовместимое изменение расхода даёт `needs_review`; повторное подтверждение требует ожидаемых фактических значений и явного согласия на изменение точной суммы.
- Динамический ориентир по последней корректной оплате более раннего периода в исходной валюте. Неизвестные суммы сохраняют presence.
- Главная: остаток календарного месяца, оценки, неизвестные суммы, неполный FX; отдельные долги прошлых месяцев. Месяц обновляется по таймеру и при возвращении во вкладку.
- Валюта отображения RUB/USD/EUR; валюты ввода соответствуют обычным счетам и операциям. Для планов используется текущий доступный FX с датой курса, для оплат — исторический контракт transactionfx.
- Новый tenant-scoped `RecurringPaymentService`, Go/TS stubs, серверная обратная ссылка из расхода, RU/EN.

Генератор выполняет ограниченные одиночные INSERT с ON CONFLICT, без финансовых движений. Диапазон более 1200 календарных месяцев для одного шаблона отклоняется целиком с ошибкой; неполный набор не возвращается. Снимок шаблона хранит `effective_month`, чтобы последующее чтение не создавало прошлые начисления по изменённому расписанию.

## Локальная проверка

- Go: recurringpayment, transaction, transactionfx, gRPC adapter и tenant guard; сборка budgetd.
- PostgreSQL 15/16 в одноразовых контейнерах: календарь и генерация, гонка восьми подтверждений при пуле из пяти соединений, идемпотентность, атомарные движения, rollback, запрет повторной привязки, unlink/delete/reconfirm, отсутствие планов в фактических totals, исторический/текущий FX и отсутствие курса, редактирование/архив с ручным исключением, запрет down с пользовательскими данными.
- Upgrade с production schema 11 до 64 и повторный запуск миграций; регрессия существующего учёта счетов на PostgreSQL 16.
- Read-only EXPLAIN точных INSERT и DELETE генератора на 12 000 начислений: INSERT использует conflict arbiter уникального периода; DELETE использует bitmap index scan по tenant/template/scheduled_month и anti join со связями. Это проверка плана, не измерение производительности production.
- Web: typecheck, 3 unit-теста (смена месяца, focus, неполные суммы), production build.
- Playwright: 4 сценария RU/EN, 390px, новый и существующий расход, двойной клик, конфликт ответа, unlink, создание шаблона; регрессия общего переключателя валют. Браузерные API используют protobuf fixtures; реальная финансовая атомарность проверяется отдельно в PostgreSQL.
- Buf lint и git diff --check.

Для браузерной сборки задавать `NEXT_PUBLIC_GRPC_BASE_URL` во время `npm run build`, а не только во время `next start`. В локальной проверке используется `http://127.0.0.1:3030/grpc`.

## Выпуск и откат

1. Сначала backend: встроенная аддитивная миграция `0064_recurring_payments` и новый RPC. Проверить schema version 64, readiness и логи.
2. Затем совместимый web. Проверить раздел, сводку и доступ между бюджетами без создания пробных production-расходов.
3. Зафиксировать отдельно CI, digest, rollout и пользовательскую приёмку: локальные тесты не подтверждают deployment.

UI можно откатить, сохранив данные. Down с непустыми таблицами намеренно запрещён. Старый binary с набором миграций только до 63 не подходит для обычного старта на schema 64: миграционный startup откажет, что проверено upgrade-тестом. Для отката backend нужен совместимый binary с сохранением новой миграции и финансового контракта.

Telegram, уведомления, частичные оплаты и создание шаблона из журнала остаются последующими этапами по исходному плану.
