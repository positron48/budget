# Автоматические курсы и валюта сводки накоплений

## Запрос

Автоматически импортировать курсы валют, загрузить историю с 01.01.2025 и обеспечить пересчёт и суммирование накоплений в выбранную валюту.

## Проверенные границы, 03.10.2026

- `migrations/0008_fx_rates.up.sql`: общая таблица `fx_rates`, уникальность пары, даты и источника; точность `NUMERIC(18,8)`.
- `internal/adapter/postgres/fx_repo.go`: только сохранённые прямые пары, ближайшая предыдущая дата. Выбор источника при одинаковой дате не согласован между одиночным и пакетным запросами.
- `internal/adapter/grpc/fx_server.go`, `web/app/fx/page.tsx`: чтение и ручная запись курсов; автоматического импортера в `cmd`, `internal`, `scripts` нет.
- `internal/usecase/asset/service.go`: `GetOverview` принимает целевую валюту и оценивает текущие остатки независимо от исторического `base_amount` операций. Отсутствующие курсы делают итог неполным. Расчёты и округление используют точную арифметику.
- `web/app/assets/page.tsx`: переключатель уже существует; общий итог и суммы по типам пересчитываются. Выбор не сохраняется. `AssetAccountCard` показывает только оригинальные остатки.
- `web/app/page.tsx`: отдельная главная сводка доходов/расходов; выбранной валюты нет, накопления в неё сейчас не включены.
- [Официальный XML API ЦБ](https://www.cbr.ru/development/sxml/) предоставляет дневной срез (`XML_daily.asp`) и историю валюты (`XML_dynamic.asp`).
- Реальный запрос `XML_daily.asp?date_req=01/01/2025` вернул дату действия **29.12.2024**, все девять иностранных валют из `ASSET_CURRENCIES`: USD, EUR, GBP, KZT, CNY, TRY, GEL, AMD, RSD. RUB — базовая валюта источника. Для начала истории нужен этот исходный срез; сохранять фактическую дату курса. Значения AMD/KZT/RSD даны за 100 единиц, TRY — за 10; требуется деление на номинал.

## Согласованные решения

Пользователь согласовал ЦБ, первый этап только `/assets` и приоритет ручного курса на ту же дату. Пересчитываются общий итог, типы и карточки; исходные суммы остаются рядом. Выбор валюты сохраняется отдельно для каждого бюджета в браузере. Главная сводка и отчёты не расширяются.

## План реализации

1. Добавить HTTP/XML адаптер ЦБ: начальный срез и история девяти валют с 01.01.2025, нормализация номинала точной арифметикой, проверка результата конечным срезом. Сохранять валюты к RUB с источником `cbr` и реальными датами действия.
2. Добавить атомарный пакетный upsert и единое чтение FX: прямые пары и кросс-курсы ЦБ через RUB; последняя дата, затем manual. Для кросс-курса сохранять в ответе более раннюю дату из двух составляющих, источник `cbr`. Исходные записи операций не менять.
3. Фоновая загрузка при старте backend и проверка нового календарного дня Москвы каждый час. Первый успешный запуск загружает всю историю, дальнейшие — последние семь дней; перезапуск повторяет полную идемпотентную загрузку. Ошибка ЦБ не блокирует API и не сохраняет частичный импорт. Отдельная CLI для явного импорта и dry-run. Изменений схемы не требуется.
4. Общий точный расчёт на web для итогов типов и карточек, сохранение выбранной валюты, дата и источник курса, неполные оценки при отсутствии курса.
5. Проверить XML/номиналы/ошибки, обратные и кросс-пары, исторические границы и приоритет manual в PostgreSQL, округление и UI переключения; затем выполнить фактический импорт и отдельно зафиксировать среду и результат. Публикация frontend/backend и локальные проверки отражаются раздельно.

## Эксплуатация

- Автозагрузчик включён по умолчанию (`FX_IMPORT_ENABLED=true`); `false` отключает его. Новые настройки Kubernetes для включения не нужны. Проверка нового дня раз в час, граница суток — Москва. Последняя успешная дата хранится в процессе; после перезапуска вся история проверяется повторно.
- Импорт не блокирует готовность API. Успех: `CBR FX import complete` с количеством котировок. Ошибка: `CBR FX import failed; retrying in one hour`. Если ЦБ недоступен, продолжают использоваться последние сохранённые курсы с их фактическими датами; состояние ошибки видно в логах.
- Ручная пара применяется к указанному направлению. Кросс-курсы строятся только из котировок `cbr`, чтобы не смешивать источники. Сначала выбирается последняя дата, затем на одинаковую дату `manual`. Одинаковая валюта всегда имеет курс 1. Округление пары — 8 знаков, денежных остатков — до младших единиц, половина от нуля.
- Первоначальный срез на 01.01.2025 сохраняет дату действия 29.12.2024. В выходные используется ближайший предыдущий курс; фиктивных ежедневных записей нет.
- Исходные остатки, сохранённые `base_amount`, обмены и движения не переписываются. Новые валютные операции могут использовать импортированную историю; существующие пересчёт не затрагивает.
- Миграций нет. Отключение автозагрузчика не удаляет историю; возвращение предыдущего приложения не удаляет данные. Предыдущая версия умеет читать только прямые пары.

Проверка без доступа к БД:

```sh
GOTOOLCHAIN=go1.25.13 go run ./cmd/fximport -from 2025-01-01 -to 2026-10-03 -dry-run
```

Импорт с установленным `DATABASE_URL` (не выводить значение в логи):

```sh
GOTOOLCHAIN=go1.25.13 go run ./cmd/fximport -from 2025-01-01 -to 2026-10-03
```

Без `-to` используется текущий день Москвы. Команда возвращает ненулевой код при ошибке и `FX import complete ... dry_run=false` только после атомарной записи. `-dry-run` не подключается к базе. Бинарник CLI собирается отдельно: `go build -o bin/fximport ./cmd/fximport`.

SQL проверки:

```sql
SELECT provider, from_currency_code, count(*), min(as_of), max(as_of)
FROM fx_rates GROUP BY provider, from_currency_code ORDER BY from_currency_code;
```

## Исправление пустой сводки для существующей сессии, 03.10.2026

Пользователь создал два наличных счёта без location и один банковский, но сводка оставалась пустой. Production подтвердил три успешных `CreateAccount`, два активных `cash`, один `bank` и три начальные сверки; запросов чтения сводки в этом сценарии не было. Данные сохранены; location не участвует в ограничении загрузки.

Причина воспроизводится при отсутствующем или пустом `budget/tenant` в localStorage: backend определяет бюджет из `tenant_id` JWT и успешно создаёт счета, но `useAssetTenant` раньше читал только отдельную настройку браузера. Из-за `enabled: ready`/`enabled: !!tenant` сводка, детали и выбор счёта не отправляли запросы.

Исправление: `authStore.getTenant()` использует явно выбранный бюджет, а при его отсутствии — `tenant_id` access token, как backend. Разбор JWT на клиенте служит только выбору UI/cache key; проверка подписи и прав остаётся на сервере. `useAssetTenant` слушает обновление авторизации, чтобы обновиться при ротации токена. Пользовательский выбор другого бюджета сохраняет приоритет.

Регрессия `web/tests/assets-session.test.tsx` использует настоящий authStore: два наличных без места и банковский счёт отображаются при отсутствующей/пустой настройке бюджета, загрузка запускается после появления токена, явный выбор не перезаписывается, повреждённый токен не ломает страницу и logout очищает вычисленный бюджет. До исправления 4 теста падали, после — все 5 проходят. Записи production не изменялись.

Проверка реального usecase `GetOverview` с production-БД (read-only, без вывода сумм) вернула для RUB, USD и EUR: `accounts=3 cash=2 bank=1 incomplete=false`. Временная проверочная программа удалена; пользовательские данные не менялись.
