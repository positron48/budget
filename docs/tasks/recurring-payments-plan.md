# Регулярные платежи и переменные начисления

Дата: 18.10.2026. Статус: первый веб-этап реализован локально. Проверки и порядок выпуска: [recurring-payments-release.md](recurring-payments-release.md). Production rollout не выполнялся.

## Цель и согласованные решения

Пользователь заводит повторяющийся расход, видит ближайшие сроки и отмечает фактическую оплату. Поддерживаются фиксированные платежи (интернет, подписки, аренда) и переменные (квартплата, электричество).

| Вопрос | Ответ пользователя |
| --- | --- |
| Что означает «Оплачено» | Создать расход или выбрать уже существующий; отдельной галочки без операции нет. |
| Сумма квартплаты до квитанции | Показывать ориентир по предыдущему месяцу либо заданную оценку, затем вводить точную сумму. |
| Первый выпуск | Веб-раздел и блок на главной; Telegram позже. |
| Дашборд | Отдельный блок «Ещё заплатить в этом месяце» с остатком обязательных платежей до конца календарного месяца. |

Остальные правила ниже — предлагаемые решения для первой версии, а не дополнительные ответы пользователя. Блокирующих вопросов по согласованному сценарию нет.

## Как было, что изменится, как станет

Сейчас в бюджетном журнале есть фактические доходы/расходы, но нет шаблона регулярного расхода и состояния оплаты отдельного периода. Расход может быть связан со счётом накоплений. Инвестиционный календарь решает отдельную задачу и не является календарём бытовых платежей.

Добавляем три понятия: шаблон, начисление за конкретный период и связь с расходом. Плановые начисления не входят в фактические расходы и не уменьшают остатки. Наступление срока не создаёт финансовую операцию.

Пример:

1. Создать «Квартплата», ежемесячно до 10-го, за предыдущий месяц, RUB, категория «Жильё», ориентир 8 000 ₽.
2. В октябре увидеть «За сентябрь · до 10 октября · примерно 8 000 ₽».
3. После квитанции указать 8 450 ₽ только для этого начисления.
4. Нажать «Отметить оплату», проверить сумму, дату и необязательный счёт; создать расход. Если расход уже внесён через журнал/бота, выбрать его.
5. Увидеть «Оплачено 8 450 ₽, 9 октября» со ссылкой на расход. Расход учитывается ровно один раз.
6. Следующее переменное начисление получает ориентир 8 450 ₽, пока не задана его точная сумма.

Приложение фиксирует сообщение пользователя об оплате; эта кнопка не отправляет деньги поставщику.

## Пользовательский сценарий первой версии

### Создание шаблона

- Название, категория расхода, валюта, необязательный счёт и комментарий.
- Периодичность: каждый месяц, квартал, год; единая модель `interval_months = 1 / 3 / 12`.
- Месяц первой оплаты и день месяца либо «последний день месяца»; необязательный последний месяц.
- Фиксированная или переменная сумма. Фиксированная сумма положительная; для переменной первоначальная оценка необязательна.
- Для ежемесячного платежа подпись «за текущий / предыдущий месяц». Период услуги и срок оплаты — разные поля; подпись не меняет дату фактического расхода.
- Часовой пояс IANA: заполняется из браузера, сохраняется в шаблоне и доступен для изменения. У tenant сейчас нет собственного часового пояса.
- Создание из существующего расхода — следующий небольшой этап; для MVP достаточно обычной формы с предзаполнением при оплате.

Предлагаемые ограничения MVP: только расходы; один полный платёж — одна операция. Частичная оплата, объединение нескольких начислений одним расходом, еженедельные расписания, счётчики/тарифы, вложения и распознавание квитанций не входят в первый выпуск. Их отсутствие не мешает вручную вводить итог квартплаты.

### Раздел «Регулярные платежи» (`/payments`)

- Основной вид — список начислений за выбранный месяц; месяцы определяются по сроку оплаты. Вкладка «Шаблоны» содержит настройки и архив.
- В строке: название, период услуги, срок, сумма с признаком «примерно / точно / неизвестна», статус, действия.
- Фильтры «Все / К оплате / Оплачено / Просрочено / Пропущено / Проверить»; поиск по названию.
- Над списком: оплачено, осталось по точным суммам, дополнительно по оценке, число начислений с неизвестной суммой и число требующих проверки.
- На главной — блок «Ещё заплатить в этом месяце» по срокам оплаты в текущем календарном месяце, включая уже просроченные в этом месяце. Оплаченные и пропущенные исключаются; будущие месяцы не входят. Месяц задаётся явно как `YYYY-MM` по локальному календарю пользователя и отображается в блоке.
- В блоке крупно показать оставшуюся известную сумму; если в неё входят оценки, подписать «примерно». Рядом раскрыть «точно / по оценке» и «ещё N платежей без суммы», если такие есть. `needs_review` выделить отдельным счётчиком без вымышленного остатка. Ни неизвестные суммы, ни недостающий FX не превращать в ноль; при них итог явно неполный.
- Ниже — ближайшие строки текущего месяца с суммой, сроком и кнопкой «Отметить оплату», ссылка «Все платежи месяца». Общая сумма считается по всем соответствующим начислениям, а не только видимым строкам, и сразу обновляется после оплаты.
- Просрочки прошлых месяцев — отдельная строка/список «Долги за прошлые месяцы», вне суммы текущего месяца и без двойного счёта. Переход к полному списку; старые долги не исчезают при смене месяца. Если все платежи месяца оплачены/пропущены и нет неизвестных состояний, показать «В этом месяце всё оплачено»; если начислений не было — «На этот месяц платежей нет».
- Из строки доступны «Указать сумму», «Изменить срок», «Отметить оплату», «Пропустить»; у оплаченного — просмотр расхода и явное снятие связи.
- RU/EN и мобильная ширина 390px обязательны.

### Суммы и состояния

Сумма и оплата — независимые измерения. «Сумма неизвестна» не является оплатой; такое начисление тоже может просрочиться.

Приоритет ожидаемой суммы: точная сумма начисления → ручная оценка начисления → последняя корректно подтверждённая оплата более раннего периода этого шаблона в той же валюте → начальная оценка шаблона → неизвестно. Для фиксированного шаблона сумма копируется в начисление как точная.

- Автоматический ориентир вычисляется при чтении, а не копируется заранее на год: после оплаты новая сумма видна в следующих начислениях. Будущая досрочная оплата не становится основанием для оценки более раннего периода.
- Неизвестная сумма хранится как NULL / отсутствующее поле, а не 0. Нулевую квитанцию в MVP можно пропустить с причиной «Нет начисления», без фиктивного расхода.
- `planned` — нет подтверждённого расхода; `paid` — связанный расход соответствует подтверждению; `skipped` — явно пропущено; `needs_review` — связанный расход изменился несовместимым образом.
- `overdue` вычисляется для неоплаченного начисления, если локальная дата уже позже `due_date`. В день срока оно ещё не просрочено. Пропущенные и оплаченные не просрочены; для `needs_review` показывается срок, но не выдумывается остаток долга.
- `paid` выводится из существующей связи и актуального расхода, не хранится независимым boolean.
- Для суммы «Оплачено» группировка в разделе идёт по начислениям выбранного месяца; подпись объясняет это. Обычные отчёты продолжают учитывать расход по `occurred_at` — например, досрочная оплата октября в сентябре входит в сентябрьские расходы.

### Подтверждение оплаты и исправления

«Отметить оплату» открывает форму с двумя вариантами:

1. **Новый расход:** предзаполнить категорию, валюту, ожидаемую сумму и счёт; дата по умолчанию — сейчас. Пользователь подтверждает фактические сумму и дату. Переменный ориентир становится точной суммой этого начисления. При расхождении с уже точной суммой явно показать её изменение перед сохранением; не считать неполную оплату полной молча.
2. **Уже внесённый расход:** поиск по операциям активного бюджета. По умолчанию предложить ту же категорию и даты рядом со сроком, разрешить расширить поиск для ранней/поздней оплаты. Обязательны тот же tenant, расход, положительная сумма, та же исходная валюта, фактическая дата не в будущем и отсутствие другой связи. Категория — подсказка, не основание автоматически менять существующую операцию. При расхождении суммы применяется то же явное уточнение начисления.

В обеих ветках записываются пользователь и время подтверждения. Нет автоматического сопоставления только по похожей сумме или тексту.

- Повтор запроса с тем же ключом не создаёт второй расход. Одновременная оплата двумя участниками с разными ключами тоже не создаёт два расхода: блокируется само начисление.
- Снятие связи сохраняет финансовую операцию и возвращает начисление к оплате. Диалог явно говорит, что расход останется в журнале; это защищает от случайного удаления уже существующей операции.
- Удаление связанного расхода штатным API удаляет связь в той же транзакции БД. Начисление снова неоплачено, движение счёта удаляется по существующим правилам.
- Изменение суммы, валюты или типа связанного расхода переводит начисление в «Проверить» по сравнению с подтверждёнными значениями. Оно не остаётся безусловно оплаченным. Доступны повторное подтверждение актуальной корректной суммы или снятие связи. Дата в будущем также требует исправления/снятия связи.
- Изменение счёта, комментария, категории или фактической даты в пределах прошлого не дублирует расход; данные отображаются из актуальной операции. Счёт и движения обновляются существующим transaction API.
- Исправить сумму уже оплаченного начисления можно через расход с последующим подтверждением; независимого изменения «точной суммы» с сохранением прежней галочки не допускаем.
- После любого успешного ответа, включая повтор старого идемпотентного запроса, клиент перечитывает текущее начисление. Сохранённый ответ старого запроса не доказывает, что расход не был позже удалён.

## Расписание и история

- Хранить календарные даты как SQL DATE / `YYYY-MM-DD`, не как UTC-полночь. Дату оплаты расхода хранить существующим TIMESTAMPTZ.
- Якорь расписания — месяц и исходный день. Для 31-го в коротком месяце берётся последний день, затем расписание возвращается к 31-му; нельзя получать даты цепочкой `AddDate` от уже сокращённого февраля.
- У начисления есть стабильный `scheduled_month` — месяц по расписанию. Уникальность `(tenant_id, template_id, scheduled_month)` не зависит от переноса `due_date`; перенос не создаёт второе начисление.
- Материализовать начисления от первого месяца до горизонта 12 месяцев вперёд при создании шаблона и перед чтением списка/сводки. Эта внутренняя операция идемпотентна и записывает только плановые строки. Для первого выпуска отдельный cron/worker не нужен: до следующего открытия приложения ничего финансового автоматически не происходит.
- При чтении прошлого/будущего периода дополнить соответствующий диапазон. Пройденные месяцы не пропускать даже после долгого отсутствия пользователя. Большой диапазон обрабатывать ограниченными пакетами с явной ошибкой/признаком незавершённости, никогда не отдавать неполный итог как полный.
- После первичного заполнения читать данные и сводные суммы согласованно; выдача и пагинация стабильны по `(due_date, id)`.
- Редактирование начисления меняет только его. Редактирование шаблона применяется со следующего месяца и не переписывает текущие/прошлые начисления, оплаты, пропуски и вручную изменённые будущие начисления.
- Перед изменением шаблона достроить прошедшие начисления по прежним настройкам. Для нетронутых будущих обновить снимки или удалить больше не входящие в расписание; будущие с ручными изменениями сохранить как исключения и перечислить в предпросмотре изменения.
- Периодичность/якорный месяц меняются явно с предпросмотром будущих дат. История хранится в снимках начислений, полная таблица версий расписаний для MVP не требуется.
- Архивирование прекращает новые начисления со следующего месяца, удаляет только нетронутые будущие планы; сохраняет текущие, прошлые и изменённые будущие исключения. Архив не закрывает старые долги. Для MVP возобновление — новый шаблон с явно заданным первым месяцем, без неожиданного заполнения периода архива.

## Валюты и фактический учёт

- Исходная валюта задаётся в шаблоне и фиксируется в начислении; общий переключатель валюты интерфейса её не меняет.
- Неоплаченные ожидаемые суммы переводить в валюту отображения по последнему доступному курсу на дату просмотра. Это оценка, в том числе для просроченных; показывать дату курса. Будущий курс неизвестен.
- Фактические расходы и оплаченные суммы пересчитывать существующим `transactionfx.Converter` с его историческим FX/snapshot-контрактом.
- Сводка содержит отдельные точные суммы, оценки и количество неизвестных. При недостающем FX — явно неполная оценка с исходными суммами, без курса 1 и фиктивного нуля.
- Прогноз не попадает в `GetTransactionsTotals`, `ReportService` или `asset_movements`. После подтверждения там появляется только обычный расход.
- Выбор счёта при оплате необязателен; без счёта меняются фактические расходы, но не остатки накоплений. С выбранным счётом сохраняются текущие ограничения валюты, архива, сверки и типов счетов.

## Данные и API

Предлагается отдельный `RecurringPaymentService` в `proto/budget/v1/recurring_payment.proto` и три таблицы. Текущая последняя миграция при подготовке плана — 0063; перед реализацией повторно проверить номер и использовать следующий свободный.

1. `recurring_payment_templates`: id/tenant, название, expense category, валюта, default account, режим суммы, fixed amount / initial estimate, первый месяц, интервал, день/последний день, смещение периода услуги, timezone, последний месяц, archived, version, автор/время создания и изменения.
2. `recurring_payment_occurrences`: id/tenant/template, scheduled_month, period label/start, due_date, снимки названия/категории/валюты/счёта/timezone/режима суммы, exact amount, optional estimate override, skipped/reason, признак ручного изменения, version, автор/время изменения. Статусы paid/overdue/needs_review вычисляются.
3. `recurring_payment_links`: tenant, occurrence_id, transaction_id, подтверждённые amount/currency/type, confirmed_by/at. Одна активная связь на начисление и на расход; снятие связи удаляет строку, не операцию. История прежних ручных привязок отдельным аудит-журналом в MVP не предусмотрена.

Ограничения: tenant во всех запросах и составных FK; уникальность периода и связи; положительные известные суммы; допустимые значения интервала, дня, режима. Для FK `(tenant_id, transaction_id)` добавить `UNIQUE(tenant_id,id)` к transactions при отсутствии. Удаление расхода каскадно удаляет только link. Удалять шаблон с историей нельзя; используется архивирование. Индексы для `(tenant_id,due_date,id)`, `(tenant_id,template_id,scheduled_month)` и поиска связи по transaction_id. Архивные счета/категории не должны мешать чтению истории, но при новой оплате требуют допустимой замены.

RPC:

- `List/Create/Update/ArchiveRecurringPaymentTemplate` — version для изменений, request_key для повторяемых команд; update возвращает/поддерживает предпросмотр затронутого будущего расписания.
- `ListPaymentOccurrences` — диапазон дат, статусы, поиск, пагинация, `target_currency_code`; ответ включает сводку по всем отфильтрованным строкам, а не только странице.
- `GetPaymentOccurrence`, `UpdatePaymentOccurrence` — сумма/срок/заметка конкретного начисления с version; нельзя редактировать оплаченный факт через плановые поля.
- `GetPaymentOverview` — явный `month` и `target_currency_code`; неоплаченные начисления этого календарного месяца, точная/оценочная части итога, счётчики неизвестных сумм и требующих проверки, ближайшие строки. Отдельная группа долгов за прошлые месяцы. Итоги не ограничены количеством возвращённых строк; текущие просрочки входят в текущий месяц только один раз.
- `ConfirmPayment` — occurrence_id, expected_version, request_key и `oneof { new_expense, existing_transaction }`; фактические сумма/дата/счёт и явное согласие на уточнение точного начисления при расхождении. Для существующего расхода передать ожидаемые критичные значения, чтобы конкурентное изменение не подтвердилось незаметно.
- `UnlinkPayment`, `SetPaymentSkipped` — version, request_key; нельзя пропустить связанную оплату без предварительного снятия связи. Возврат из пропуска явный.

Ответ начисления содержит исходные суммы, отображаемые эквиваленты, источник оценки/дату курса, статус, actual transaction summary и признаки неполных данных. Для optional amounts использовать presence, а не sentinel 0. Номера существующих protobuf-полей не менять. В `Transaction` можно добавить необязательный `payment_occurrence_id` для обратной ссылки/предупреждения при редактировании; его заполняет сервер, обычный UpdateTransaction не принимает запись связи через поле модели.

Новый сервис защищается membership guard; owner/admin/member могут вести общий список аналогично текущим операциям. Cross-tenant IDs не раскрывают чужие данные. Ошибки: `InvalidArgument` для данных, `NotFound` для недоступного объекта, `FailedPrecondition` для уже оплаченного/недопустимого счёта/отсутствующего FX, `Aborted` для устаревшей версии или изменения payload с тем же ключом. Причины — стабильные коды для RU/EN, без SQL-текста в UI.

## Порядок реализации

1. **Модель и расписание.** Добавить `internal/domain/recurring_payment.go`, `internal/usecase/recurringpayment/` с чистыми функциями календаря, оценки и статусов. Зафиксировать примеры квартплаты/подписки и пограничные даты тестами.
2. **Миграция и хранилище.** Таблицы, FK/индексы и `internal/adapter/postgres/recurring_payment_repo.go`. Идемпотентное построение горизонта, сохранение снимков, версии и изменения будущих периодов. Проверить свежую БД и upgrade с текущей схемы.
3. **Атомарное подтверждение.** Repo/UoW открывает внешний `financialWrite` для `confirm_recurring_payment`, блокирует начисление, проверяет версию/связь, затем вызывает существующий transaction usecase внутри того же контекста и записывает link. Не вызывать два независимых RPC «создать расход» и «связать» с браузера. Внешний ключ/результат сохраняются один раз: вложенный `financialWrite` намеренно не создаёт отдельную запись идемпотентности. Ошибка категории, FX, счёта или связи откатывает всё.
4. **API и совместимость.** Новый proto, Go/TS stubs, gRPC adapter, mapping ошибок, membership guard, регистрация в `cmd/budgetd/main.go`, обратная ссылка в чтении операций. Проверить удаление и редактирование обычным API и влияние на вычисляемый статус; без изменения старого финансового контракта.
5. **Веб-раздел.** `web/app/payments/page.tsx`, `web/components/payments/`, клиент, навигация, RU/EN. Переиспользовать селекторы категории/счёта и разбор денег. При расширении NewTransactionForm отделить поля от отправки, чтобы подтверждение вызывало именно ConfirmPayment.
6. **Главная и согласованность.** Блок «Ещё заплатить в этом месяце» и отдельные долги прошлых месяцев. После подтверждения инвалидировать платежи, `transactions`, `transactionsTotals`, `assets`, `dashboard-monthly`, `dashboard-recent`, `monthly`, `summary`. Обычные update/delete расхода инвалидируют и связанные платежи. Ключи содержат tenant, месяц и валюту, переключение бюджета не показывает предыдущий кэш. При смене локального месяца и возвращении во вкладку обновлять месяц блока и данные.
7. **Проверка и выпуск.** Фокусные тесты, миграции, production-сборка, приёмка сценариев; затем backend и совместимый web. Telegram — отдельная последующая задача.

Во всех командах оплаты и редактирования связей использовать существующий порядок блокировок tenant → строки начисления/расхода → счета. Read-time генерация планов блокирует шаблон; её порядок с update/archive должен совпадать. Конкурентные сценарии проверять в настоящем PostgreSQL.

## Проверки и критерии приёмки

- Календарь: 28/29 февраля, 30/31-е, конец месяца, квартал/год, граница года, перенос срока без дубля, первый/последний месяц, Moscow/Madrid и DST. Смена timezone просмотрщика не меняет срок шаблона.
- Переменные суммы: неизвестно → оценка → точная сумма → оплата; приоритет ручной оценки; новая оплата меняет только автоматические ориентиры; изменение/удаление предыдущей оплаты корректно меняет источник оценки.
- Расписание: повторная генерация, два одновременных открытия, долгое отсутствие пользователя, обновление шаблона, архив с долгом, вручную исправленное будущее начисление. Статус просрочки определяется по внедряемым часам, без ожидания реального времени.
- Учёт PostgreSQL: новый расход/движение/link атомарны, повтор одного ключа и гонка разных ключей, rollback на ошибке, один расход нельзя связать дважды, link чужого tenant запрещён, архивный/несовместимый счёт отклоняется.
- Исправления: unlink не удаляет расход, delete расхода снимает оплату и движение, изменение суммы приводит к «Проверить», корректное переподтверждение возвращает «Оплачено», перенос расхода между счетами не удваивает движение.
- Отчёты: генерация планов не меняет реальные totals/balance; после оплаты расход учитывается один раз и по фактической дате; старая операция до сверки подчиняется существующим правилам накоплений.
- Валюты: RUB/USD/EUR отображение; будущий план по текущему доступному курсу, расход по историческому; отсутствующий FX/неизвестная сумма не дают ложного полного итога.
- Web: фиксированная подписка и квартплата, выбор существующего расхода, двойной клик, конфликт версии, смена tenant, RU/EN, 390px, переход с главной к просроченному прошлому месяцу, согласованное обновление отчётов.
- Дашборд: остаток именно за календарный месяц, исключение оплаченных/пропущенных, включение текущих просрочек, отдельный прошлый долг без двойного счёта, оценка/неизвестная сумма/нет FX, итог по всем строкам, уменьшение после оплаты, состояния «всё оплачено» и «платежей нет», переход на следующий месяц без перезагрузки страницы.

## Миграция, выпуск и откат

- Миграция аддитивная. Существующие расходы и остатки не переписываются; автоматического поиска «всех подписок» и backfill связей нет. Первое начисление определяется явно при создании шаблона.
- Учесть миграционные тесты с жёстко заданной текущей версией схемы, включая `internal/adapter/postgres/migrate_upgrade_integration_test.go`.
- Сначала выпустить backend со схемой и API, затем web. Встроенные миграции должны успешно завершиться до включения нового интерфейса.
- CI, digest/rollout, readiness и пользовательская приёмка — разные доказательства; записать отдельно при реализации. Production-проверка по умолчанию read-only; реальные финансовые операции ради проверки не создавать.
- Откат UI не удаляет расписание/связи. Не выполнять down-миграцию с пользовательскими начислениями; down должен явно отказать при непустых новых таблицах. Расходы, созданные при подтверждении, остаются обычными расходами.
- Прежде чем обещать откат backend, проверить совместимость старого binary с новой версией миграций. FK на link и вычисляемый статус должны сохранять целостность и при update/delete старым клиентом.

## После первого выпуска

Telegram-напоминания и подтверждение оплаты используют этот же API, а не отдельный учёт бота. Перед тем этапом отдельно выбрать получателей в общем бюджете, расписание/часовой пояс, согласие на уведомления и подавление дублей. Ни отправка уведомлений, ни изменения budget-bot в текущий план реализации не входят.

Неблокирующие продуктовые расширения: недельные интервалы; частичные оплаты; одна операция на несколько начислений; регулярные доходы; квитанции/счётчики; создание шаблона из журнала. Их добавление требует отдельного уточнения контракта, особенно распределения суммы операции.
